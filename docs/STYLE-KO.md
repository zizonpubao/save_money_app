# 한국어 문체 규칙 (README · 문서 · 앱 문구)

한국 개발자가 쓴 GitHub README처럼 읽혀야 한다. 번역한 느낌이 나면 실패다.

## 톤
- 본문은 **합니다체**로 통일. "~합니다 / ~입니다 / ~됩니다". 해요체·반말 섞지 않는다
- 표 안, 목록 항목, 그림 라벨은 **명사형이나 짧은 구**로 끝낸다. "저장 시 햅틱" (O) / "저장하면 햅틱이 울립니다" (X)
- 자기 해설 금지. "그게 의도된 설계입니다", "~하게 설계했습니다" 같은 문장은 삭제하거나 사실만 남긴다
- 과장·감탄 금지. "놀라운", "강력한", "완벽하게" 같은 수식어는 쓰지 않는다

## 문장
- 한 문장에 정보 하나. 쉼표로 둘 이상 이으면 나눈다
- 주어를 생략해도 되면 생략한다. "이 앱은 ~합니다" 보다 "~합니다"
- 능동으로 쓴다. "~에 의해 처리됩니다" (X) → "~가 처리합니다" (O)
- 조사·어미 한 번 더 읽어 어색한 걸 잡는다: "~에 대해", "~을 통해", "~에 있어서", "~함으로써" 는 거의 항상 지울 수 있다

## 번역투 치환 표
| 피할 표현 | 대신 |
|---|---|
| ~을 돌려준다 (return) | ~을 보여준다 / ~이 나온다 |
| 장치, 메커니즘 | 기능, 방식 |
| ~을 거쳐 | ~을 지나 / 순서대로 |
| ~에 위치한 | ~에 있는 |
| ~을 제공한다 | ~이 있다 / ~을 지원한다 |
| ~하는 것을 허용한다 | ~할 수 있다 |
| 유저 | 사용자 |
| 퍼포먼스, 이슈, 핸들링 | 성능, 문제, 처리 |
| ~적인 (형용사 남용) | 명사 그대로 또는 다른 형용사 |
| 이것은 / 그것은 (대명사 시작) | 대상을 직접 쓰거나 생략 |

## 외래어·표기
- 굳어진 개발 용어는 영어 그대로: commit, push, PR, migration 은 한글로 "커밋, 푸시, 마이그레이션" 도 가능하나 한 문서 안에서 하나로 통일
- 숫자·단위: `4,500원`, `2026년 9월 23일 (수)`. 띄어쓰기 규칙은 앱 문구와 같게
- 이모지는 헤딩과 표 라벨에만. 본문 문장 안에는 넣지 않는다

## 확인 방법
다듬은 뒤 소리 내어 읽듯이 한 번 훑는다. 숨이 차거나 "누가 이렇게 말하지?" 싶은 문장이 남아 있으면 다시 고친다.
